# SQL

## What it is

SQL (Structured Query Language) is the language you use to talk to a relational database. A **relational database** keeps data in **tables**: a table is a grid where each **row** is one record and each **column** is one named, typed field. SQL has statements to create tables (**DDL**, data definition language), to add or change rows (**DML**, data manipulation language) and to ask questions (**queries**, which start with `SELECT`). A statement ends with a semicolon. Words such as `SELECT` are not case sensitive; this repository writes them in capitals.

## Why this repository uses it

The lesson is about a design choice: store the rental shop's data as linked tables, or as documents. The SQL files are the tables version. The key idea is that a database can enforce a rule itself (no item is rented twice for overlapping dates), so that no program, however buggy or however many run at once, can break it.

## How it works underneath

You send a statement as text to the database server. The server **parses** it (checks the grammar), **plans** it (chooses how to find the rows, see [postgresql.md](postgresql.md)) and **executes** it. A **constraint** is a rule attached to a table that the server checks on every change: `NOT NULL` (a value must exist), `CHECK` (a condition must hold), `PRIMARY KEY` (unique and not null, and the row's identity), `REFERENCES` (a foreign key: the value must exist in another table) and `EXCLUDE` (no two rows may conflict under given operators). A statement that breaks a constraint fails and changes nothing.

A **transaction** is a group of statements that succeed or fail together. `BEGIN` starts one, `COMMIT` keeps its changes and `ROLLBACK` throws them away. A **schema** is a named folder of tables inside a database; the default is called `public`.

Dates in this repository are **half-open**: a rental from `2026-11-01` to `2026-11-04` occupies the nights of the 1st, 2nd and 3rd, and the 4th is the day the item comes back, so the next rental may start that very day. In notation, `[1st, 4th)`: square bracket includes, round bracket excludes.

## Walkthrough of this repository's use

### `reset.sql`

```sql
-- Drops the lab's tables so `make db` can rebuild them from scratch. Not part of the run order.
SET client_min_messages = warning;
DROP TABLE IF EXISTS rentals, items, customers CASCADE;
DROP TABLE IF EXISTS item_documents, customer_documents CASCADE;
```

`--` starts a comment. `SET client_min_messages = warning` lowers how chatty the server is for this session, so `DROP TABLE IF EXISTS` does not print a notice for each table that is missing. `DROP TABLE IF EXISTS a, b, c CASCADE` deletes several tables in one statement; `IF EXISTS` makes it succeed when a table is absent, and `CASCADE` also deletes things that depend on the tables (such as the foreign keys from `rentals`). The second statement drops the two document tables created by `document_model/001_documents.sql`.

### `001_schema.sql`: header and the two small tables

```sql
-- DDL: the relational model of the equipment-rental shop (lesson steps 2 and 4).
-- Run order: 001_schema.sql, 002_seed.sql, migrations/001_exclusion_constraint.sql, then 003_queries.sql and
-- 004_constraint_demo.sql (make db applies the first three; make queries and make demo run the others).
-- The tables are the lesson's step-2 design. The rule that makes a double booking impossible is step 4's change
-- and lives in the migration, so the lesson's "before" and "after" can both be run.

CREATE TABLE customers (
    customer_id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name        text NOT NULL CHECK (name <> '')
);

CREATE TABLE items (
    item_id    integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name       text          NOT NULL CHECK (name <> ''),
    daily_rate numeric(8, 2) NOT NULL CHECK (daily_rate > 0)
);
```

- The comment lines record the run order and say that the double-booking rule is deliberately left out of this file (it is lesson step 4, in the migration) so the "before" and "after" can both be run.
- `CREATE TABLE customers ( ... );` defines a table. Inside the parentheses each column is a name, a type and constraints.
- `customer_id integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`: `integer` is a four-byte whole number. `GENERATED BY DEFAULT AS IDENTITY` makes the server number new rows automatically from a counter called a **sequence**; `BY DEFAULT` still lets an insert supply its own number (the seed does). `PRIMARY KEY` means unique, never empty, and the row's address for other tables; it also creates an index (a lookup structure kept sorted for fast search).
- `name text NOT NULL CHECK (name <> '')`: `text` is a string of any length; `NOT NULL` forbids a missing value (NULL means "unknown"); `<>` means "not equal", so the empty string is refused.
- `items` adds `daily_rate numeric(8, 2) NOT NULL CHECK (daily_rate > 0)`. `numeric(8, 2)` is an exact decimal with at most 8 digits, 2 of them after the point; money must not use floating point, which rounds. The check forbids free or negative rates. The extra spaces only align columns.

### `001_schema.sql`: `rentals`

```sql
CREATE TABLE rentals (
    rental_id   integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    item_id     integer   NOT NULL REFERENCES items (item_id),
    customer_id integer   NOT NULL REFERENCES customers (customer_id),
    -- Half-open [first rental day, day the item comes back), so "touching" rentals (one ends the day the next
    -- starts) do not overlap. The check refuses empty ranges. For daterange the [) form is also what PostgreSQL
    -- stores for every input (it rewrites '[a,b]' as '[a,b+1)'), so the two bound tests only state the rule;
    -- they cannot fail. See the closed-range case in 004_constraint_demo.sql.
    during      daterange NOT NULL
        CHECK (NOT isempty(during) AND lower_inc(during) AND NOT upper_inc(during))
);
```

- `item_id integer NOT NULL REFERENCES items (item_id)` is a **foreign key**: every rental must name an existing item, and an item with rentals cannot be deleted. Same for `customer_id`.
- `during daterange NOT NULL` stores a range of dates in a single column. `daterange` is a PostgreSQL type that holds a lower and an upper bound and knows whether each bound is included.
- The comment explains the half-open convention and a PostgreSQL detail: for `daterange`, every input is stored in the `[)` form, so `'[a,b]'` becomes `[a, b+1)`. This is because dates are discrete (there is a "next day"), and PostgreSQL rewrites ranges of discrete types into one canonical form.
- `CHECK (NOT isempty(during) AND lower_inc(during) AND NOT upper_inc(during))`: `isempty` is true for a range containing no dates; `lower_inc` and `upper_inc` say whether the lower and upper bound are included. The check states the convention: not empty, lower bound in, upper bound out. Only the first test can fail; the other two always hold for a `daterange` and are kept to say the rule out loud.

### `001_schema.sql`: indexes and comments

```sql
-- Foreign keys index the parent side only; the child columns need their own indexes.
-- History of one customer, newest or oldest first.
CREATE INDEX rentals_customer ON rentals (customer_id, lower(during));
-- Returns due on a given day.
CREATE INDEX rentals_return_day ON rentals (upper(during));

COMMENT ON TABLE rentals IS 'One row per rental of one item for a half-open date range.';
COMMENT ON COLUMN rentals.during IS 'Half-open daterange [first rental day, return day). The return day is free again.';
```

- The comment says: a foreign key does not index the referencing column in PostgreSQL (the primary key of the parent is indexed, the child column is not), so the child columns that queries use need their own indexes.
- `CREATE INDEX rentals_customer ON rentals (customer_id, lower(during))` builds an index on two things: the customer, then the first day of the rental, computed by the function `lower(during)`. An index on an **expression** like this is used by queries that write the same expression. It serves "one customer's history, oldest first".
- `CREATE INDEX rentals_return_day ON rentals (upper(during))` serves "which rentals come back on this day".
- `COMMENT ON TABLE ... IS '...'` and `COMMENT ON COLUMN` attach a description to the table and the column, stored in the database itself; `psql`'s `\d+` shows them.

### `002_seed.sql`

```sql
-- DML: the hand-checkable data of the lesson. 2 customers, 4 items, 7 rentals.
-- Dates are half-open: the second date is the day the item comes back, not a rental day.

INSERT INTO customers (customer_id, name) VALUES (1, 'Ada'), (2, 'Bruno');

INSERT INTO items (item_id, name, daily_rate) VALUES
    (1, 'Drill', 10),
    (2, 'Ladder', 8),
    (3, 'Tent', 15),
    (4, 'Kayak', 20);

INSERT INTO rentals (rental_id, item_id, customer_id, during) VALUES
    (1, 1, 1, daterange('2026-11-01', '2026-11-04')),  -- Drill, Ada, 3 days
    (2, 1, 2, daterange('2026-11-04', '2026-11-06')),  -- Drill, Bruno; touches rental 1 (allowed: 11-04 is free again)
    (3, 2, 1, daterange('2026-11-02', '2026-11-09')),  -- Ladder, Ada, 7 days
    (4, 3, 2, daterange('2026-10-20', '2026-10-23')),  -- Tent, Bruno
    (5, 1, 1, daterange('2026-12-01', '2026-12-03')),  -- Drill, Ada
    (6, 3, 1, daterange('2026-11-07', '2026-11-10')),  -- Tent, Ada
    (7, 2, 2, daterange('2026-10-25', '2026-10-28'));  -- Ladder, Bruno
```

- `INSERT INTO customers (customer_id, name) VALUES (1, 'Ada'), (2, 'Bruno');` adds two rows; the column list names the order of the values, and the strings are single-quoted (double quotes mean identifiers in SQL).
- `daterange('2026-11-01', '2026-11-04')` calls the constructor function; with two arguments it builds the half-open `[)` range, which is why rental 2 may start on `2026-11-04`, the day rental 1 ends.
- The comments at the end of each line (`-- Drill, Ada, 3 days`) are for the human checking the data.

```sql
-- Explicit ids were given above, so move each identity sequence past them.
DO $$ BEGIN PERFORM setval(pg_get_serial_sequence('customers', 'customer_id'), (SELECT max(customer_id) FROM customers)); END $$;
DO $$ BEGIN PERFORM setval(pg_get_serial_sequence('items', 'item_id'), (SELECT max(item_id) FROM items)); END $$;
DO $$ BEGIN PERFORM setval(pg_get_serial_sequence('rentals', 'rental_id'), (SELECT max(rental_id) FROM rentals)); END $$;

ANALYZE customers;
ANALYZE items;
ANALYZE rentals;
```

- The seed gave explicit ids, so the sequences behind the identity columns still start at 1 and the next automatic insert would collide with row 1. The `DO $$ ... $$` block is an anonymous program written in PL/pgSQL, PostgreSQL's procedural language; `$$` is a quote that avoids escaping the single quotes inside. `PERFORM expression` runs an expression and discards the result. `pg_get_serial_sequence('customers', 'customer_id')` returns the sequence's name, `(SELECT max(customer_id) FROM customers)` is a **subquery** returning the highest id, and `setval(sequence, value)` moves the counter so the next number issued is value + 1.
- `ANALYZE table;` makes the server sample the table and store statistics (row count, value spread) that the planner uses to choose plans.

### `003_queries.sql`: the five questions

```sql
-- The five questions of lesson step 1, answered on the hand-checked data (make queries).
-- "Today" is 2026-11-04 and "next weekend" is 2026-11-07 up to, not including, 2026-11-09.

-- 1. Free next weekend: items with no rental that overlaps the weekend. Expected: Drill, Kayak.
SELECT i.item_id, i.name
FROM items i
WHERE NOT EXISTS (
    SELECT 1 FROM rentals r
    WHERE r.item_id = i.item_id AND r.during && daterange('2026-11-07', '2026-11-09')
)
ORDER BY i.item_id;

-- 1b. The same question for one item, the frequent form (200 a day): is the Ladder free next weekend? Expected: f.
SELECT NOT EXISTS (
    SELECT 1 FROM rentals r WHERE r.item_id = 2 AND r.during && daterange('2026-11-07', '2026-11-09')
) AS ladder_is_free;
```

- The header fixes the lesson's dates: "today" is 2026-11-04 and "next weekend" is 2026-11-07 up to, not including, 2026-11-09.
- Query 1: `SELECT i.item_id, i.name FROM items i` reads the table `items` and gives it the **alias** `i`. `WHERE NOT EXISTS ( ... )` keeps an item only if the subquery returns no row. The subquery is **correlated**: it mentions `i.item_id` from the outer query. `SELECT 1` returns a dummy value (only existence matters). `r.during && daterange('2026-11-07', '2026-11-09')` uses the **overlap operator** `&&`: true when two ranges share at least one date. `ORDER BY i.item_id` sorts the result. Expected: Drill, Kayak.
- Query 1b asks the same for one item. `SELECT NOT EXISTS (...) AS ladder_is_free` returns a single true/false value; `AS` names the output column. For the Ladder it is `f` (false), since rental 3 covers the weekend.

```sql
-- 2. Ada's rental history, oldest first. Expected: rentals 1, 3, 6, 5 (by start date).
SELECT r.rental_id, i.name AS item, lower(r.during) AS first_day, upper(r.during) AS return_day
FROM rentals r
JOIN items i USING (item_id)
WHERE r.customer_id = (SELECT customer_id FROM customers WHERE name = 'Ada')
ORDER BY lower(r.during), r.rental_id;

-- 3. Returns today: rentals whose return day is 2026-11-04. Expected: rental 1 (Drill, Ada).
SELECT r.rental_id, i.name AS item, c.name AS customer
FROM rentals r
JOIN items i USING (item_id)
JOIN customers c USING (customer_id)
WHERE upper(r.during) = DATE '2026-11-04'
ORDER BY r.rental_id;
```

- Query 2: `JOIN items i USING (item_id)` joins each rental to its item on the shared column name `item_id`. `lower(r.during) AS first_day` and `upper(r.during) AS return_day` extract the bounds. The `WHERE` picks Ada's id with a subquery on her name. `ORDER BY lower(r.during), r.rental_id` sorts by start date and uses the id to break ties so the order is always the same.
- Query 3: two joins, one per table, and `upper(r.during) = DATE '2026-11-04'`. `DATE '2026-11-04'` is a typed literal: a string turned into a date. Expected: rental 1.

```sql
-- 4. Revenue per item and month, the month being the one the rental starts in.
--    upper - lower on a daterange is the number of days. Expected: Drill 2026-11 50, Drill 2026-12 20,
--    Ladder 2026-10 24, Ladder 2026-11 56, Tent 2026-10 45, Tent 2026-11 45.
SELECT i.name AS item,
       to_char(lower(r.during), 'YYYY-MM') AS month,
       sum((upper(r.during) - lower(r.during)) * i.daily_rate) AS revenue
FROM rentals r
JOIN items i USING (item_id)
GROUP BY i.name, to_char(lower(r.during), 'YYYY-MM')
ORDER BY i.name, month;

-- 5. Items never rented. Expected: Kayak.
SELECT i.item_id, i.name
FROM items i
WHERE NOT EXISTS (SELECT 1 FROM rentals r WHERE r.item_id = i.item_id)
ORDER BY i.item_id;
```

- Query 4 computes revenue: `upper(r.during) - lower(r.during)` subtracts two dates, which gives a whole number of days; multiplied by `i.daily_rate`. `sum( ... )` adds the values per group. `to_char(lower(r.during), 'YYYY-MM')` formats a date as year and month text, so a rental belongs to the month it starts in. `GROUP BY i.name, to_char(...)` makes one output row per item and month; every selected value that is not inside `sum` must be listed there. `ORDER BY i.name, month` sorts by the output alias `month`.
- Query 5: `NOT EXISTS (SELECT 1 FROM rentals r WHERE r.item_id = i.item_id)` keeps the items with no rental at all. Expected: Kayak.

### `migrations/001_exclusion_constraint.sql`

```sql
-- Lesson step 4: let the database refuse a double booking.
-- Adding the constraint validates the existing rows, so it fails if any item already has overlapping rentals;
-- on a table that has had none, it is a single statement. Building the GiST index locks writes to `rentals`
-- while it runs; on a big live table you would plan that window.

-- An exclusion constraint mixes `=` on an integer and `&&` on a range in one GiST index, and GiST has no
-- operator class for plain integers until this extension adds one. Without it the ALTER fails with
-- "data type integer has no default operator class for access method gist".
CREATE EXTENSION IF NOT EXISTS btree_gist;

-- No two rows may have the same item and overlapping ranges. A violation is SQLSTATE 23P01.
-- The constraint's GiST index also answers "is item X free on these dates" with an index scan.
ALTER TABLE rentals
    ADD CONSTRAINT rentals_item_id_during_excl EXCLUDE USING gist (item_id WITH =, during WITH &&);

COMMENT ON CONSTRAINT rentals_item_id_during_excl ON rentals IS 'An item is never rented twice for overlapping dates (SQLSTATE 23P01).';
```

- A **migration** is a script that changes an existing schema; this one is lesson step 4. The header warns that adding the constraint checks every existing row and that building the index blocks writes to the table while it runs.
- `CREATE EXTENSION IF NOT EXISTS btree_gist;` loads an extension (an add-on module shipped with PostgreSQL). A GiST index (Generalized Search Tree) can index ranges, but has no built-in way to index plain integers. `btree_gist` adds it. Without it the next statement fails with "data type integer has no default operator class for access method gist".
- `ALTER TABLE rentals ADD CONSTRAINT rentals_item_id_during_excl EXCLUDE USING gist (item_id WITH =, during WITH &&);` adds an **exclusion constraint**, named so errors are readable. It says: no two rows may exist where the `item_id`s are equal (`=`) and the `during` ranges overlap (`&&`) at once. A violation raises error code (SQLSTATE) `23P01`, `exclusion_violation`. The server enforces it with a GiST index on `(item_id, during)`.
- The last statement stores a comment on the constraint.

### `004_constraint_demo.sql`

```sql
-- What the constraint does (lesson step 4), as psql shows it. Each case runs in its own transaction and is
-- rolled back, so the hand-checked data stays as it was. ON_ERROR_STOP is off so the refusal is printed
-- and the script goes on (make demo).
\set ON_ERROR_STOP off

\echo '-- overlap: Drill from 11-03 to 11-05 collides with rental 1 (11-01 to 11-04); expect SQLSTATE 23P01'
BEGIN;
INSERT INTO rentals (rental_id, item_id, customer_id, during) VALUES (8, 1, 2, daterange('2026-11-03', '2026-11-05'));
ROLLBACK;

\echo '-- touching: Drill from 11-06 starts the day rental 2 ends; expect INSERT 0 1'
BEGIN;
INSERT INTO rentals (rental_id, item_id, customer_id, during) VALUES (9, 1, 2, daterange('2026-11-06', '2026-11-08'));
ROLLBACK;

\echo '-- closed range: [] counts the return day as a rental day, so a rental that only touches is refused'
BEGIN;
INSERT INTO rentals (rental_id, item_id, customer_id, during) VALUES (10, 4, 1, '[2026-11-01,2026-11-04]');
SELECT during AS stored_as FROM rentals WHERE rental_id = 10;
INSERT INTO rentals (rental_id, item_id, customer_id, during) VALUES (11, 4, 2, daterange('2026-11-04', '2026-11-06'));
ROLLBACK;

\echo '-- an empty range is refused by the check'
BEGIN;
INSERT INTO rentals (rental_id, item_id, customer_id, during) VALUES (12, 4, 1, 'empty');
ROLLBACK;
```

- `\set ON_ERROR_STOP off` and `\echo '...'` are not SQL: a backslash begins a `psql` client command (see [psql.md](psql.md)). `\set` changes a psql variable so that after a failed statement the script continues; `\echo` prints a line.
- Each case runs `BEGIN; ... ROLLBACK;`, so nothing stays in the database.
- Case 1 inserts a Drill rental for 11-03 to 11-05, which overlaps rental 1: the server refuses with `23P01`.
- Case 2 inserts 11-06 to 11-08, starting the day rental 2 ends. Touching is allowed, so the output is `INSERT 0 1` (the zero is a historical field, the one is the row count).
- Case 3 writes a closed range as text, `'[2026-11-01,2026-11-04]'`; PostgreSQL stores it as `[2026-11-01,2026-11-05)`. `SELECT during AS stored_as` shows that. The next insert, a Kayak rental starting 11-04, now collides with it and is refused.
- Case 4 inserts `'empty'`, the empty range, which the `CHECK` constraint of the schema refuses with `23514`.

### `bulk/100k_rentals.sql`

```sql
-- Lesson step 6: 100,000 rentals so the plans mean something (make bulk).
-- 1,000 items get 100 rentals of 3 days each, 4 days apart, so none overlap. The dates run from 2024-01-01 to
-- early 2025, clear of the hand-checked rentals in 2026. Items 5 to 1000 and customers 3 to 500 are added first.
-- The rental ids start at 1,001 so they do not collide with the seed's rentals 1 to 7.
-- Run it through `make bulk`: that drops the exclusion constraint for the load and adds it back afterwards, which builds
-- its index once and re-checks every row. With the constraint in place each insert is checked through the GiST index
-- and 100,000 rows take minutes.
-- Note: items 1 to 4 now have rentals, so "never rented" no longer answers Kayak; `make db` restores the seed.

INSERT INTO customers (customer_id, name)
SELECT n, 'Customer ' || n FROM generate_series(3, 500) AS n
ON CONFLICT DO NOTHING;

INSERT INTO items (item_id, name, daily_rate)
SELECT n, 'Item ' || n, 5 + n % 20 FROM generate_series(5, 1000) AS n
ON CONFLICT DO NOTHING;

INSERT INTO rentals (rental_id, item_id, customer_id, during)
SELECT 1000 + n, 1 + n % 1000, 1 + n % 500,
       daterange(DATE '2024-01-01' + (n / 1000) * 4, DATE '2024-01-01' + (n / 1000) * 4 + 3)
FROM generate_series(1, 100000) AS n;

DO $$ BEGIN PERFORM setval(pg_get_serial_sequence('customers', 'customer_id'), (SELECT max(customer_id) FROM customers)); END $$;
DO $$ BEGIN PERFORM setval(pg_get_serial_sequence('items', 'item_id'), (SELECT max(item_id) FROM items)); END $$;
DO $$ BEGIN PERFORM setval(pg_get_serial_sequence('rentals', 'rental_id'), (SELECT max(rental_id) FROM rentals)); END $$;

-- Without fresh statistics the planner works from the seed's tiny numbers and the plans mislead.
ANALYZE customers;
ANALYZE items;
ANALYZE rentals;
```

- `generate_series(3, 500) AS n` produces the numbers 3 to 500 as rows. `SELECT n, 'Customer ' || n` builds a name with the string joining operator `||`. `INSERT ... SELECT` inserts the rows a query returns. `ON CONFLICT DO NOTHING` skips a row whose key already exists, so rerunning is harmless.
- Items 5 to 1000 get a rate `5 + n % 20`: `%` is the remainder after division, so rates run 5 to 24.
- The rentals use `1000 + n` as the id, `1 + n % 1000` as item and `1 + n % 500` as customer. `n / 1000` is whole-number division (it drops the fraction), so rentals 1 to 999 share a start offset of 0 days, the next thousand 4 days later and so on. `DATE '2024-01-01' + 4` adds days to a date. Each rental is 3 days with a 1-day gap, so none overlap and the constraint can be added afterwards.
- The three `DO $$` lines reset the sequences, and the `ANALYZE` lines refresh statistics, for the same reasons as in the seed.

### `document_model/001_documents.sql`

```sql
-- Lesson step 3, made runnable: the document design, stored as JSONB so no second database is needed.
-- Each row is one document, the way a document store keeps it. The point of the file is what is missing from it:
-- no key, foreign key, check or exclusion constraint can see inside the `booked` and `rentals` arrays.

CREATE TABLE item_documents (
    item_id integer PRIMARY KEY,
    doc     jsonb   NOT NULL
);

CREATE TABLE customer_documents (
    customer_id integer PRIMARY KEY,
    doc         jsonb   NOT NULL
);

COMMENT ON TABLE item_documents IS 'Items collection: availability is easy because the booked ranges live here.';
COMMENT ON TABLE customer_documents IS 'Customers collection: history is easy because the rentals live here.';

-- The two copies of each rental the design needs: one in the item, one in the customer.
INSERT INTO item_documents VALUES
    (1, '{"name": "Drill", "dailyRate": 10, "booked": []}'),
    (2, '{"name": "Ladder", "dailyRate": 8, "booked": []}');

INSERT INTO customer_documents VALUES
    (1, '{"name": "Ada", "rentals": []}'),
    (2, '{"name": "Bruno", "rentals": []}');
```

The document design, stored as `jsonb` (binary JSON: a column that holds a whole JSON document). JSON is text with objects `{"key": value}` and arrays `[...]`. Each row is one document. The primary key is on the id, but nothing can look inside the arrays. `INSERT INTO item_documents VALUES (...)` without a column list fills the columns in table order. The Drill and Ladder have an empty `booked` array; Ada and Bruno an empty `rentals` array.

### `document_model/002_double_booking.sql`

```sql
-- Two requests book the drill for overlapping dates. In the document design both are accepted (make demo-documents).
-- The relational model refuses the second with SQLSTATE 23P01; see 004_constraint_demo.sql.

-- Request A: Ada, Drill, 11-01 to 11-04. Two writes, one per copy, not atomic with each other across documents.
UPDATE item_documents
SET doc = jsonb_set(doc, '{booked}', doc->'booked' || '[{"rentalId": 1, "customerId": 1, "from": "2026-11-01", "to": "2026-11-04"}]')
WHERE item_id = 1;
UPDATE customer_documents
SET doc = jsonb_set(doc, '{rentals}', doc->'rentals' || '[{"rentalId": 1, "itemId": 1, "from": "2026-11-01", "to": "2026-11-04"}]')
WHERE customer_id = 1;

-- Request B: Bruno, Drill, 11-03 to 11-05. Nothing checks the ranges inside the array, so this succeeds too.
UPDATE item_documents
SET doc = jsonb_set(doc, '{booked}', doc->'booked' || '[{"rentalId": 2, "customerId": 2, "from": "2026-11-03", "to": "2026-11-05"}]')
WHERE item_id = 1;
UPDATE customer_documents
SET doc = jsonb_set(doc, '{rentals}', doc->'rentals' || '[{"rentalId": 2, "itemId": 1, "from": "2026-11-03", "to": "2026-11-05"}]')
WHERE customer_id = 2;

-- The drill is double booked. This is the check the application would have to write, and race on.
SELECT a.value->>'rentalId' AS first_rental,
       b.value->>'rentalId' AS second_rental,
       daterange((a.value->>'from')::date, (a.value->>'to')::date) *
       daterange((b.value->>'from')::date, (b.value->>'to')::date) AS overlapping_days
FROM item_documents d,
     jsonb_array_elements(d.doc->'booked') WITH ORDINALITY AS a(value, ord),
     jsonb_array_elements(d.doc->'booked') WITH ORDINALITY AS b(value, ord)
WHERE d.item_id = 1 AND a.ord < b.ord
  AND daterange((a.value->>'from')::date, (a.value->>'to')::date) &&
      daterange((b.value->>'from')::date, (b.value->>'to')::date);

-- A customer's history comes from one document, with no join: this is where documents are easier.
SELECT jsonb_array_length(doc->'rentals') AS adas_rentals FROM customer_documents WHERE customer_id = 1;
```

- `UPDATE table SET column = value WHERE condition` changes existing rows. `jsonb_set(doc, '{booked}', new)` returns a copy of the document with the array at path `booked` replaced. `doc->'booked'` reads the array as JSON and `|| '[{...}]'` appends one element (`||` joins two JSON arrays). Two updates per request, one for the item's copy and one for the customer's copy; nothing makes them atomic together.
- Request B overlaps request A, yet both updates succeed: no key, check or exclusion constraint can see inside an array.
- The check query: `jsonb_array_elements(d.doc->'booked') WITH ORDINALITY AS a(value, ord)` turns the array into rows with a position column `ord`; joining it to itself pairs up bookings, `a.ord < b.ord` keeps each pair once. `a.value->>'rentalId'` reads a field as text (`->>`), `(...)::date` casts text to a date, and `*` on two ranges returns their intersection. The final `daterange(...) && daterange(...)` keeps overlapping pairs.
- The last query counts Ada's rentals with `jsonb_array_length`: one document, no join, which is where documents are easier.

### The six `explain` queries

```sql
-- The frequent availability check (200 a day): is item 777 free from 2024-02-01 to 2024-02-04?
-- Before the step-4 constraint nothing indexes (item_id, during); after it the constraint's GiST index answers this.
EXPLAIN (ANALYZE, BUFFERS)
SELECT NOT EXISTS (
    SELECT 1 FROM rentals WHERE item_id = 777 AND during && daterange('2024-02-01', '2024-02-04')
) AS item_is_free;
```

```sql
-- Which of the 1,000 items are free for a three-day window? One probe per item.
EXPLAIN (ANALYZE, BUFFERS)
SELECT i.item_id, i.name
FROM items i
WHERE NOT EXISTS (
    SELECT 1 FROM rentals r WHERE r.item_id = i.item_id AND r.during && daterange('2024-02-01', '2024-02-04')
)
ORDER BY i.item_id;
```

```sql
-- One customer's history, oldest first: rentals_customer (customer_id, lower(during)) gives the rows already in order.
EXPLAIN (ANALYZE, BUFFERS)
SELECT r.rental_id, i.name AS item, lower(r.during) AS first_day, upper(r.during) AS return_day
FROM rentals r
JOIN items i USING (item_id)
WHERE r.customer_id = 42
ORDER BY lower(r.during), r.rental_id;
```

```sql
-- Rentals coming back on one day: rentals_return_day (upper(during)).
EXPLAIN (ANALYZE, BUFFERS)
SELECT r.rental_id, i.name AS item, c.name AS customer
FROM rentals r
JOIN items i USING (item_id)
JOIN customers c USING (customer_id)
WHERE upper(r.during) = DATE '2024-03-12'
ORDER BY r.rental_id;
```

```sql
-- The daily report: every rental is read once, so a full scan is the right plan. Frequency is once a day.
EXPLAIN (ANALYZE, BUFFERS)
SELECT i.name AS item,
       to_char(lower(r.during), 'YYYY-MM') AS month,
       sum((upper(r.during) - lower(r.during)) * i.daily_rate) AS revenue
FROM rentals r
JOIN items i USING (item_id)
GROUP BY i.name, to_char(lower(r.during), 'YYYY-MM')
ORDER BY i.name, month;
```

```sql
-- Items with no rentals, once a week. An anti join over all rentals.
EXPLAIN (ANALYZE, BUFFERS)
SELECT i.item_id, i.name
FROM items i
WHERE NOT EXISTS (SELECT 1 FROM rentals r WHERE r.item_id = i.item_id)
ORDER BY i.item_id;
```

Each file is a query from the lesson prefixed with `EXPLAIN (ANALYZE, BUFFERS)`. `EXPLAIN` prints the plan the server chose instead of the result; `ANALYZE` makes it actually run the query and report real times and row counts; `BUFFERS` adds how many 8-kilobyte pages were read from memory (`shared hit`) or from disk (`read`). The queries are the shop's questions made large: one item's availability (q1, 200 times a day), free items (q2), a customer's history (q3), returns on a day (q4), the monthly revenue report (q5) and never-rented items (q6). Where the captured plans are discussed: `sql/explain/results.md`.

## Mistakes people make

- **Using `float` for money**: it rounds. This repository uses `numeric(8, 2)`.
- **Assuming a foreign key creates an index** on the child column. It does not; the schema adds the indexes it needs.
- **Checking availability in the application and then inserting**: two programs can both pass the check. The constraint is the only rule that cannot be raced.
- **Forgetting that `NULL` is not equal to anything**, even to `NULL`; the schema uses `NOT NULL` throughout.
- **Closed ranges** (`[a,b]`) that silently become `[a,b+1)`; case 3 of the demo shows it.

## Check yourself

1. What does `&&` do on two ranges? *True when they share at least one point.*
2. Why is `GENERATED BY DEFAULT AS IDENTITY` followed by `setval` in the seed? *Explicit ids do not advance the sequence, so it is moved past them.*
3. What is the difference between `WHERE` and `HAVING`/`GROUP BY` in query 4? *`WHERE` filters rows before grouping; `GROUP BY` forms one row per item and month.*
4. What error code does a double booking raise? *SQLSTATE `23P01`.*
5. Why does the demo wrap every case in `BEGIN ... ROLLBACK`? *So the hand-checked data is unchanged afterwards.*
